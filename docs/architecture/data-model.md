# FraudGuard — Data Model

**Version:** 1.0 (baseline) · **Date:** 2026-09-07

PostgreSQL is the durable system of record (ADR-003 — never read on the hot path). This
document is the design; migrations implementing it are a Phase 3 deliverable in
`packages/persistence`. Every table and index below states why it exists, so a reviewer
never has to guess.

---

## Entity-relationship sketch

```
 users (external)          merchants (external)         devices (external)
  referenced by id          referenced by id              referenced by id
        │                          │                            │
        └──────────────┬───────────┴──────────────┬─────────────┘
                        ▼                          ▼
                  transactions ──1───1──▶ decisions ──1───1──▶ outbox_events
                        │                     │                (ADR-006, pruned
                        │                     │                 after publish)
                        │                     ▼
                        │              risk_policies (versioned, referenced by
                        │               decisions.policy_version)
                        │                     │
                        │                     ▼
                        │              model_versions (referenced by
                        │               decisions.model_version)
                        │
                        └───0..1──▶ fraud_cases ──1───N──▶ case_reviews
                                                            (one terminal row —
                                                             the case lifecycle
                                                             only transitions once)

                        audit_events (append-only, references any aggregate
                                       by aggregate_type + aggregate_id —
                                       no foreign key, by design: see below)
```

`users`, `merchants`, `devices` are **not** tables FraudGuard owns — in this prototype
they are synthetic identifiers generated by `packages/testkit` (FR-018) and referenced by
id only. A real deployment would own or federate to these from the payment platform;
modelling them here would be scope the project does not need (§2.2 of requirements.md).

## Tables

### `transactions`

The record of every authorization request received, independent of outcome.

| Column                                | Type                                                     | Why                                                                                                                                                                                                    |
| ------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `transaction_id`                      | `text` PK                                                | Client-supplied, validated by `idSchema` — safe character set enforced at the API boundary before it ever reaches SQL.                                                                                 |
| `user_id`, `merchant_id`, `device_id` | `text`                                                   | Synthetic identifiers (SECURITY.md) — never a real customer identity.                                                                                                                                  |
| `amount_minor_units`                  | `bigint`                                                 | Integer minor units, never a float — see `Money` in `packages/domain`.                                                                                                                                 |
| `currency`                            | `char(3)`                                                | ISO 4217.                                                                                                                                                                                              |
| `payment_method`                      | `text`                                                   | A tokenised reference only. **No column exists for a PAN** — this is the schema-level half of "no code path can receive a card number" (SECURITY.md); there is nowhere to put one even if one arrived. |
| `ip_address`                          | `inet`                                                   | Native Postgres type — enables range/subnet queries for IP-risk features without string parsing.                                                                                                       |
| `status`                              | `text` (check constraint against `TRANSACTION_STATUSES`) | Mirrors `packages/domain`'s lifecycle enum exactly — a status value the domain doesn't recognise cannot be persisted.                                                                                  |
| `received_at`                         | `timestamptz`                                            |                                                                                                                                                                                                        |

**Indexes**

| Index                        | Why                                                                                                                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PK (transaction_id)`        | Primary lookup — every query in the system starts from a transaction id.                                                                                                  |
| `(user_id, received_at)`     | Supports "this user's transaction history" queries (review-api investigation screen, Brief §31) and any cold-path recomputation of a feature window from durable history. |
| `(merchant_id, received_at)` | Supports merchant-level investigation and the merchant-risk feature's cold-path recomputation.                                                                            |

### `decisions`

One row per scored transaction. Immutable once written (`packages/domain`'s
`FraudDecision` is never edited).

| Column               | Type                                       | Why                                                                                                                                                                                                                 |
| -------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `transaction_id`     | `text` PK, FK → `transactions`             | 1:1 with the transaction it scored.                                                                                                                                                                                 |
| `decision`           | `text` (check: `ALLOW`/`REVIEW`/`BLOCK`)   |                                                                                                                                                                                                                     |
| `risk_score`         | `numeric(5,4)`                             | Fixed-point, not float — a risk score feeding a policy threshold comparison must not be subject to floating-point representation error at the boundary value.                                                       |
| `reasons`            | `jsonb`                                    | Client-safe reasons only (`toClientSafeReasons` output) — internal rule detail is never persisted here; it lives in structured logs / traces for debugging, which have a shorter retention and a narrower audience. |
| `policy_version`     | `text`, FK → `risk_policies`               |                                                                                                                                                                                                                     |
| `model_version`      | `text`, FK → `model_versions`              | FR-012 — every decision's provenance is queryable.                                                                                                                                                                  |
| `scoring_provider`   | `text` (check against `SCORING_PROVIDERS`) |                                                                                                                                                                                                                     |
| `degraded`           | `boolean`                                  | ADR-005 — never inferred, always recorded.                                                                                                                                                                          |
| `degraded_reason`    | `text` (check against `DEGRADED_REASONS`)  |                                                                                                                                                                                                                     |
| `decided_at`         | `timestamptz`                              |                                                                                                                                                                                                                     |
| `processing_time_ms` | `real`                                     | Feeds the performance report (Phase 9) from durable history, independent of the Prometheus histogram's retention window.                                                                                            |

**Indexes**

| Index                              | Why                                                                                                                                                                                     |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PK (transaction_id)`              |                                                                                                                                                                                         |
| `(decided_at)`                     | Time-range queries for reporting and the performance report.                                                                                                                            |
| `(degraded) WHERE degraded = true` | Partial index — the degraded-decision ratio (ADR-005 visibility requirement) is a small, frequently-queried subset; a partial index keeps it cheap regardless of total decision volume. |

### `fraud_cases`

| Column           | Type                                    | Why                                                                                                                                                                                                                                                     |
| ---------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `case_id`        | `uuid` PK                               |                                                                                                                                                                                                                                                         |
| `transaction_id` | `text`, FK → `transactions`, **unique** | The unique constraint is what makes case-creation idempotent at the database level (RISK-005) — a duplicate `transaction.decided` event attempting a second insert for the same transaction fails the constraint rather than creating a duplicate case. |
| `status`         | `text` (check against `CASE_STATUSES`)  |                                                                                                                                                                                                                                                         |
| `created_at`     | `timestamptz`                           |                                                                                                                                                                                                                                                         |
| `reviewed_at`    | `timestamptz`, nullable                 |                                                                                                                                                                                                                                                         |
| `reviewer_id`    | `text`, nullable                        | From the authenticated caller (ASM-006) — never client-supplied.                                                                                                                                                                                        |
| `review_reason`  | `text`, nullable                        |                                                                                                                                                                                                                                                         |

**Indexes**

| Index                            | Why                                                                                                                                                                        |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PK (case_id)`                   |                                                                                                                                                                            |
| `UNIQUE (transaction_id)`        | Idempotency backstop, as above.                                                                                                                                            |
| `(status) WHERE status = 'OPEN'` | Partial index — this **is** the review queue query (`GET /api/v1/fraud/cases?status=OPEN`), and it stays small regardless of how many cases have accumulated historically. |

### `risk_policies`

| Column                                               | Type           | Why                                                                                                                                                                                                                                                                  |
| ---------------------------------------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `policy_version`                                     | `text` PK      |                                                                                                                                                                                                                                                                      |
| `allow_max`, `block_min`                             | `numeric(5,4)` |                                                                                                                                                                                                                                                                      |
| `degraded_allow_max`, `degraded_block_min`           | `numeric(5,4)` | Mirrors `RiskPolicy` in `packages/domain`; a `CHECK` constraint enforces the same anti-loosening invariant `isValidRiskPolicy` checks in code — belt and suspenders, since this table can in principle be modified by a path other than the validated config loader. |
| `weight_rules`, `weight_model`, `weight_behavioural` | `numeric(5,4)` | `CHECK` that they sum to 1.0 within tolerance.                                                                                                                                                                                                                       |
| `active`                                             | `boolean`      | Exactly one row may be active — enforced by a partial unique index `UNIQUE (active) WHERE active = true`.                                                                                                                                                            |
| `created_at`                                         | `timestamptz`  |                                                                                                                                                                                                                                                                      |

**Why a table instead of only `.env`:** the `.env` values are the _bootstrap_ policy;
this table is what makes FR-006's "thresholds are configurable at runtime without
redeployment" true — an operator can insert a new version and flip `active` without
restarting `fraud-api`. `packages/feature-store`'s Redis cache holds the active policy
for hot-path reads (ADR-002); this table is its source of truth and its cold-path
history.

### `model_versions`

| Column          | Type              | Why                                                                                                                                                                           |
| --------------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_version` | `text` PK         |                                                                                                                                                                               |
| `provider_name` | `text`            | `stub` / `rules` / `ml`.                                                                                                                                                      |
| `description`   | `text`            |                                                                                                                                                                               |
| `registered_at` | `timestamptz`     |                                                                                                                                                                               |
| `active`        | `boolean`         | Same "exactly one active" pattern as `risk_policies`.                                                                                                                         |
| `metrics`       | `jsonb`, nullable | The full `ModelMetrics` shape (precision, recall, F1, ROC-AUC, PR-AUC, FPR, FNR, inference latency) — `NULL` for `stub`/`rules`, populated for a genuine ML model (Phase 10). |

### `outbox_events`

Full definition and rationale in [ADR-006](../adr/ADR-006-transactional-outbox.md) — not
repeated here. One line worth restating: this table is **not** durable history. It is a
work queue drained by the relay; `audit_events` is the durable history.

### `audit_events`

| Column           | Type                                                 | Why                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`             | `bigserial` PK                                       | Monotonic, cheap, and never reused — appropriate for an append-only log where "insertion order" is itself meaningful.                                                                                                                                                                                                                                                                                                      |
| `event_id`       | `uuid`, **unique**                                   | The dedup backstop referenced in the Kafka catalogue — a unique constraint violation on replay is the final line of defence beneath application-level `eventId` checks.                                                                                                                                                                                                                                                    |
| `aggregate_type` | `text` (`transaction` / `case` / `model` / `policy`) |                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `aggregate_id`   | `text`                                               | **Deliberately no foreign key.** An audit log must remain valid and queryable even if the row it describes is later deleted (it won't be, in this design — nothing is hard-deleted — but the audit log's correctness must not _depend_ on that). A FK would also force `audit_events` to know about every possible aggregate table, coupling the one table meant to be maximally generic to the schema of everything else. |
| `action`         | `text`                                               |                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `actor_id`       | `text`, nullable                                     |                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `detail`         | `jsonb`                                              |                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `occurred_at`    | `timestamptz`                                        |                                                                                                                                                                                                                                                                                                                                                                                                                            |

**Indexes**

| Index                                         | Why                                                                                    |
| --------------------------------------------- | -------------------------------------------------------------------------------------- |
| `PK (id)`                                     |                                                                                        |
| `UNIQUE (event_id)`                           | Dedup backstop.                                                                        |
| `(aggregate_type, aggregate_id, occurred_at)` | The investigation-screen query: "everything that happened to transaction X, in order." |

**Enforcement.** `AuditRepository` (`packages/persistence`) exposes no `update`/`delete`
method — append-only today is enforced at the application layer, not a database-role
`REVOKE`. **Correction, noticed while touching adjacent docs during Phase 7:** this
paragraph previously claimed database-privilege-level enforcement; that was never
actually true in this prototype — every service connects as one shared Postgres role
(the migration runner included), so a `REVOKE` would either block migrations too or,
if the role is the database owner (it is, locally), have no effect at all. Migration
0002's own comment and `AuditRepository`'s doc comment are accurate; this file was not.
Real least-privilege roles are Phase 11's.

## What is deliberately not modelled

- **Users, merchants, devices as owned entities** — synthetic, referenced by id only
  (§2.2 out of scope).
- **A `features` table.** Features are derived, hot-path state living in Redis
  (ADR-002); Postgres holds the transaction history that lets features be _rebuilt_, not
  a persisted copy of the features themselves.
- **Soft-delete columns anywhere.** Nothing in this system is ever deleted — a fraud
  decision or case that turns out to be wrong gets a new state (e.g. a re-review), not a
  deletion. This is what "immutable audit trail" (FR-008) means in schema terms.
