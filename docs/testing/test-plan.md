# FraudGuard — Test Plan

**Version:** 1.0 · **Date:** 2026-09-12 (Phase 8)

Companion to [test-strategy.md](./test-strategy.md) (the why/approach per test type) — this
is the concrete "what exists, what it tests, why, and what failure it would catch" per test
case, for the tiers Phase 8 actually delivers: resilience, the producer↔consumer contract,
and E2E. Unit tests (300+, `packages/*/src/**/*.test.ts`) and the existing integration
suite carry their own what/why/catches in each test file's own doc comments — re-listing
every one here would drift from the source of truth the moment either changed; this
document indexes them by file instead of duplicating their content.

## 3. End-to-end — the journeys that must never break

| Test                                | Test file                              | What it proves                                                                                                                                                                                                                                     | What failure it would catch                                                                                                                                                                                         |
| ----------------------------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `E2E-001` Full REVIEW lifecycle     | `tests/e2e/full-lifecycle.e2e.test.ts` | Scored REVIEW → case created (event-worker) → listed and approved (review-api, real HTTP) → all FOUR actions (received, decided, case created, case reviewed) land in the durable audit trail — the full chain, not pieces of it proven separately | FR-008's "full basis" claim being true for pieces of the REVIEW path but not the whole of it; a review action that doesn't actually close the loop back through the outbox/audit system                             |
| `E2E-002` Degraded path, end to end | `tests/e2e/full-lifecycle.e2e.test.ts` | A Redis-degraded decision's `degraded`/`degradedReason` survive all the way into the durable `audit_events` record, not just the HTTP response                                                                                                     | ADR-005's visibility requirement #2 ("the flag and reason are persisted... so historical analysis can separate degraded from healthy decisions") being true for the response but silently false for the audit trail |

Deliberately two tests, not many — test-strategy.md §3.5's own rule: E2E is the fewest,
slowest tier, kept to the journeys that must never break, each proving something no
existing integration test already chains together in one continuous run (see the doc
comment at the top of the test file itself for exactly which gaps each one closes).

## 4. Where everything else lives

- **Unit** (300+ tests): `packages/*/src/**/*.test.ts`. Each file's own doc comments state
  what/why/catches per test — `packages/domain` is the pyramid's base (zero I/O, exhaustive
  coverage of rule boundaries, score combination, decision thresholds, lifecycle
  transitions, as `docs/testing/test-strategy.md` §3.1 describes).
- **Integration** (≈40 tests): `tests/integration/*.integration.test.ts`, one file per
  feature area (scoring, feature-store, event-worker, review-api, observability, demo
  scenarios, policy admin). Each carries its own what/why/catches per test.
- **Architecture**: `tests/architecture/hot-path.test.ts` — ADR-003's import-graph
  enforcement, unchanged since Phase 3.
- **Security**: Phase 11's, per `docs/security/threat-model.md` §6.
- **Load**: Phase 9's, per `docs/testing/test-strategy.md` §3.8; results land in
  [test-results/](./test-results/).

## 5. Honest gaps, not hidden ones

One ADR-005 row (`fraud-api` instance loss) and its `RT-INST-001` test strategy entry
remain **not** tested, for the reason stated in §1 above: the infrastructure it would
need to exercise for real (a gateway/load balancer) does not exist yet
(`architecture.md` §14, still open), and building one solely to satisfy this phase's
checklist would mean testing against a prop rather than the real thing — exactly what
this project's own rules forbid (Brief §19, §45). Revisited the moment a gateway
exists — tracked here, and in `docs/requirements/traceability-matrix.md`, as
`PLANNED`, not quietly dropped.

The ML provider row (`RT-ML-001`) was the SAME kind of deferral through Phase 8 — no
`MLScoringProvider` existed yet — and was delivered in Phase 10 once one did; see §1's
table above.
